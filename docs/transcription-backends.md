# 转录后端对比：whisper + 文本 LLM  vs  单一 omni 模型

> 这是一份脱敏后的技术记录，用于说明为什么把转录后端从 `whisper-large-v3`
> 换成了多模态模型（omni）。原始数据来自某一天的全天录音，录音内容已移除，
> 仅保留可复现的方法与量化指标。

## 一、对比设置

| | 旧方案 | 新方案 |
| --- | --- | --- |
| 转录 | `whisper-large-v3`，OpenAI 兼容 `audio/transcriptions` | 多模态模型（omni），`chat/completions` + `input_audio` |
| LLM | 独立的文本模型 | 同一个 omni 模型 |
| 切分 | 按整点 | 定长 `segment_seconds`（本例 600s） |
| 并发 | 6 | 6 |

- 音频来源：一天的全天录音，16kHz 单声道 PCM。
- 旧方案产物已存在于 `data/text/<date>/` 与 `data/summary/<date>.md`。
- 新方案跑在独立临时目录，未写入 `data/`。

## 二、转录层对比

| 指标 | 旧 whisper | 新 omni | 备注 |
| --- | --- | --- | --- |
| 有效段数 | 全部有效 | 有若干判废段 | 判废由复读退化守卫拦下 |
| 润色后总字数 | 基准 | 约 4.1x | |
| 语速密度 | 明显偏低 | 回到正常区间 | 中文正常语速 4-5 字/秒 |

### 旧方案的两个系统性失败

1. **每小时只转出开头一小段，其余整段丢失**：多个整点文件结尾断在半句，
   对照新方案逐句对齐可确认它只覆盖了该小时的前约 10 分钟，大量内容缺失。
2. **凭空生成口播**：在无语音片段上 hallucinate 出「欢迎订阅」「点赞打赏」之类的内容，
   经单独询问模型「这段音频里有没有人说话」验证为幻觉。

另有若干同音错字。

### 新方案的问题

- **判废段**：复读退化被守卫拦下（判废后不落脏文本，但该段确实没转出来）。
- **非语音片段输出括号描述**（如「（持续的键盘敲击声）」），会混进正文。
- **纯音乐段可能「听」出歌词**，且同一段两次转录结果可能不同 —— 推理服务即使在
  `temperature=0` 下也不保证完全确定。

## 三、summary 层对比

之前 `LLMClient.call` 曾把 `max_tokens` 硬编码为 256，导致每份 summary 都在半句处
被截断；该问题已修复，`llm.max_tokens` 现为可配置项（默认 8192）。

把两套转录文本喂给**同一个 LLM**、同一套 `SUMMARY_PROMPT` 重新生成后对比：
新方案产出的 summary 落到具体、可执行的颗粒度，旧方案则多停留在「参加了某个活动」
这类空话，并把幻觉内容原样写进了总结。

## 四、结论

**转录质量：omni 明显胜出**——字数、密度、逐句对齐后的错字表现都更好，且没有
whisper 那种「整段丢失 + 口播幻觉」的系统性失败。

**代价：**

- 存在复读退化导致的判废段（可通过调 `frequency_penalty` 或对判废段重试改善）。
- 非语音片段会输出括号描述。
- 依赖服务端支持音频输入（如 vLLM 需装 `vllm[audio]`），并受单次音频时长硬限制，
  段长必须 ≤ 服务端上限。
- 音频走 JSON + base64，请求体较大，内存峰值随并发线性上升。
